# Exchange, несколько доменов и общие почтовые TLS-порты

## Exchange / Outlook

В «Сервисы → Добавить сервис» выберите **Microsoft Exchange / Outlook**.

1. Укажите основной домен и дополнительные имена, например `mail.example.org` и `autodiscover.example.org`. Выберите один или несколько сертификатов, совместно покрывающих все имена.
2. Укажите внутренние серверы Exchange. Шаблон предлагает HTTPS к серверу; проверка его сертификата включена. Если организация использует свой CA, добавьте его в системное хранилище или настройте `ca_bundle`. Отключение проверки допустимо только как осознанный выбор для доверенной сети.
3. Разверните нужные строки путей. Шаблон создаёт OWA, Autodiscover, MAPI, ActiveSync, EWS, RPC, ECP и OAB; каждому опубликованному пути соответствует свой backend и HTTP-проверка `/<служба>/healthcheck.htm` с ожидаемым кодом 200. Регистр путей по умолчанию не учитывается.
4. Пустой список серверов пути наследует общий пул и его последующие изменения. При необходимости задайте отдельные адреса `IP:порт`, балансировку, таймаут и страницу проверки только для этого пути. ActiveSync предлагает длительный таймаут сервера. Таймаут клиента уже существующего общего входа сохраняется; его глобальные настройки не меняются автоматически.
5. Корень `/` по умолчанию перенаправляется на `/owa`. ECP по умолчанию **закрыт с ответом 403**; если он нужен, явно выберите для `/ecp` действие «Опубликовать» и настройте доступ.

В списке публикаций можно раскрыть «Проверки служб»: состояние показывается отдельно по компонентам. Имена backend-пулов привязаны к пути, а не его позиции; перестановка списка не переносит `server-state` другой службе.

По остальным путям используется общий пул публикации. Если требуется закрыть отдельный префикс, добавьте путь с действием «Закрыть». Более длинные пути имеют приоритет. Ручные публикации чужих доменов остаются на месте; мастер не захватывает уже опубликованный вручную домен целиком.

Подход с проверками каждого компонента описан в [документации Microsoft Exchange](https://learn.microsoft.com/en-us/exchange/architecture/client-access/load-balancing).

## Общий SMTPS / IMAPS / POP3S / TLS-порт

В шаблоне защищённого почтового протокола включите **«Разделять общий TLS-порт по имени сервера (SNI)»**, перечислите домены и укажите собственный пул серверов этой организации. Создайте следующую публикацию на том же IP/порту с другим списком доменов и пулом.

- **Сертификат на HAProxy:** маршрутизация использует `ssl_fc_sni`. Возможен обычный TCP к внутреннему серверу или отдельный TLS-сеанс к нему. Во втором случае включите «Внутренний сервер тоже использует TLS», задайте его TLS-порт и проверку сертификата/SNI.
- **Сквозной TLS:** HAProxy анализирует ClientHello через `req.ssl_sni`, не расшифровывает соединение и отправляет его выбранному TLS-серверу. Сертификат остаётся на сервере.
- **Клиенты без SNI:** можно выбрать одну публикацию как сервер по умолчанию. Если fallback не настроен, клиент без подходящего SNI не подключится. При дополнении ручного входа его существующий `default_backend` сохраняется.

Дубли доменов, два fallback на одном порту и смешивание несовместимых режимов TLS блокируются до применения. Ограничения источников по IP действуют также на fallback.

**SMTP 25 и submission 587 с STARTTLS не имеют SNI при выборе начального backend.** `ssl_fc_sni` на обычном TCP-входе 587 не работает. Для этих сценариев используйте общий пул, отдельные внешние IP/порты либо выполняйте маршрутизацию получателей на почтовом сервере. Мастер не пытается выбирать SMTP-сервер по произвольному фрагменту письма.

Различие полей TLS описано в [руководстве HAProxy](https://docs.haproxy.org/2.8/configuration.html#7.3.3-ssl_fc_sni) и [описании req.ssl_sni](https://docs.haproxy.org/2.8/configuration.html#7.3.5-req.ssl_sni).

## Редиректы, исключения и проверки

- Можно направить `/` на локальный путь или полный HTTP(S)-адрес.
- HTTP → HTTPS сохраняет выбранный домен и поддерживает нестандартный внешний TLS-порт.
- В HTTP-исключениях перечислите префиксы, например `/test` или `/.well-known/acme-challenge`: они остаются на HTTP и передаются тому же серверу. `X-Forwarded-Proto` отражает фактический протокол клиента.
- Доступны проверка точного HTTP-кода, HTTP-методы GET/HEAD/OPTIONS, SMTP EHLO, TLS-рукопожатие, пороги успешных/неудачных проверок и журналирование изменений health.
- TLS-проверка порта проверяет рукопожатие без доверия к CA и не добавляет повторное шифрование к сквозному трафику. Проверка TLS-сертификата при реальном соединении с внутренним сервером настраивается отдельно.
- Опционально добавляются заголовки `X-Frame-Options: SAMEORIGIN` и `X-Content-Type-Options: nosniff`.

Глобальные `stats socket`, журналирование, chroot, cipher policy, `server-state-file`, errorfile и остальные уже существующие настройки сохраняются. Пример рабочей организации не импортируется в конфиг текущего сервера. Автоматически не копируются публичный admin socket, общий `ssl-server-verify none`, незавершённые `unless` или ошибочные правила SNI для STARTTLS.
