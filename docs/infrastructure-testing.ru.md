# Работа с существующим HAProxy: изменения в 0.12

Для расширенного импорта ACL и общих пулов в 0.13 см. [новую инструкцию](acl-import.ru.md). Ниже описано поведение версии 0.12.

Эта версия исправляет ошибки, обнаруженные при установке на действующую инфраструктуру. Она не переписывает неизвестные правила приблизительными аналогами.

## Перед изменениями

В разделе «Сервисы» отображается результат проверки **исходной** конфигурации через `haproxy -c -V`, версия SSL-библиотеки и обнаруженные несовместимые DH-настройки AWS-LC. В окне применения исходная и предлагаемая конфигурации показаны отдельно. Вывод включает предупреждения; пароли и ключи скрыты. Структурированная диагностика API содержит уровень сообщения, строку, секцию и директиву, когда HAProxy сообщил её местоположение.

Для AWS-LC кнопка «Просмотреть исправление настроек DH» предлагает закомментировать только `ssl-dh-param-file` и `tune.ssl.default-dh-param`. Изменение требует обычной проверки diff и применения. TLS, сертификаты и политика шифров не отключаются. Другие ошибки, включая отсутствующие файлы, исправляйте по диагностике в редакторе; Studio не удаляет ссылки автоматически.

## Публикация самой Studio

1. Добавьте сервис, тип **«HAProxy Studio — эта панель»**.
2. Укажите публичный домен и выберите покрывающий его сертификат.
3. Для двухступенчатой схемы TCP/SNI → локальный HTTPS выберите существующий внутренний HTTPS-вход. Внешний порт остаётся 443, внутренний может быть 8443.
4. Адрес локальной панели и `base_path` подставляются из настроек. Префикс удалять не нужно.
5. На шаге проверки подтвердите обновление публичного адреса самой панели.
6. Проверьте diff и примените изменения. После успеха браузер перейдёт на новый адрес; войдите заново.

`public_url` сохраняется как `https://домен[:порт]`, отдельно от `base_path`. Смена требует доступного для записи постоянного JSON-файла настроек, указанного через `STUDIO_CONFIG`. Обновлённый systemd-unit разрешает запись `/etc/haproxy-studio`; установщик обновляет unit, существующий JSON не перезаписывает. При монтировании JSON только для чтения в Docker автоматическая смена адреса недоступна. Старый файл настроек сохраняется в закрытом каталоге резервной копии. При ошибке reload или локальной проверки API/интерфейса конфигурация HAProxy восстанавливается, адрес не меняется. Изменение только `public_url` не требует reload HAProxy.

Проверки Host, Origin, CSRF и атрибут Secure для HTTPS сохраняются. Старый Host после перехода не разрешается. Публичный DNS и внешний доступ необходимо подготовить заранее: локальная проверка не подтверждает работу внешнего NAT, DNS и firewall.

По умолчанию HAProxy направляет `/` и точный путь без завершающего слеша на `/haproxy-admin/`. Приложение также самостоятельно исправляет отсутствие слеша после проверки Host и сохраняет query string.

## RD Web: редирект выполняет HAProxy

Выберите **«RDS: RD Web — редирект на HAProxy»**. Для существующего сервиса RD Web измените тип этой же публикации, вместо создания второй на том же домене.

- Обычный портал: корень `/` → `/RDWeb/`.
- HTML5: корень `/` → `/RDWeb/webclient/`.
- Код 302, только GET и HEAD; query string сохраняется, другие пути и методы передаются IIS.
- Сертификат клиентов установлен на HAProxy. По умолчанию до Windows используется отдельное HTTPS-соединение с проверкой сертификата.
- Портал должен существовать в IIS. Выбор HTML5 не устанавливает компонент webclient.

Для RD Gateway сохраняется отдельный шаблон сквозного TLS. HTTP-прокси RD Web не является заменой опубликованного и проверенного RD Gateway. При сквозном TLS HAProxy не может перенаправлять HTTPS-запросы; для этого режима остаётся [инструкция IIS](iis-rdweb-redirect.ru.md).

## Сертификаты

Импорт сохраняет все PEM-блоки цепочки. Можно загрузить fullchain PEM, PFX/P12 или сертификат, ключ и отдельный CA Bundle. Проверяются пара сертификат/ключ, порядок цепочки и подписи предоставленных промежуточных сертификатов. Недостающий issuer и отсутствие доверенного корпоративного корня могут требовать знания вашей PKI: предупреждение не означает автоматическое доверие новому CA. Настройте `ca_bundle` для частного CA.

В разделе сертификатов видны сроки, пересечения SAN/CN и типы ключей. Пересечение имён у RSA и ECDSA не считается безусловной ошибкой. Добавление отличающегося сертификата того же типа ключа поверх пересекающегося ручного сертификата на существующем bind блокируется с объяснением.

Чтобы обновить используемый сертификат:

1. Загрузите новый PEM через мастер, не применяя дополнительную публикацию.
2. Откройте «Сертификаты» → старый сертификат → «Заменить сертификат».
3. Выберите загруженный новый сертификат. Просмотрите список зависимостей, fingerprint и проверку HAProxy.
4. Примените. Старый PEM сохраняется в резервной копии, новый устанавливается атомарно по прежнему пути. При ошибке reload восстанавливается старый PEM.
5. Проверьте реальный сертификат с клиентского компьютера:

```bash
openssl s_client -connect YOUR_DOMAIN:443 -servername YOUR_DOMAIN </dev/null 2>/dev/null |
  openssl x509 -noout -fingerprint -sha256 -dates
```

Замените `YOUR_DOMAIN`. После reload автоматически сравнивается fingerprint на локальных bind с прямым `crt` или каталогом сертификатов, включая `accept-proxy`. При несовпадении или ошибке соединения выполняется откат. Для `crt-list` автоматическая проверка пока не реализована. Внешний адрес проверяйте отдельно: он может указывать на другой узел. Загруженный исходный PEM не удаляется автоматически; неиспользуемый файл можно удалить через интерфейс. Побайтово одинаковые повторные загрузки управляемых PEM не создают дубликат.

## Обнаружение, частичное управление и импорт

В «Сервисах» показаны управляемые публикации и обнаруженные связи frontend → backend, включая дополнительные `.cfg`. Обнаружение не изменяет конфигурацию и не зависит от возможности полного импорта. Общий backend не копируется. Служебный TCP → локальный HTTPS-мост остаётся в техническом разделе маршрутов и не дублируется как отдельное приложение.

Для ручных пулов доступно **частичное управление адресами и портами серверов**. Имена, порядок серверов, TLS, проверки, тайм-ауты, балансировка, параметры server, неизвестные директивы и комментарии остаются прежними. Перед применением показаны все затронутые входы. Защищённые пулы панели и управляемые блоки через этот редактор не меняются.

Связанные Exchange backend с известными страницами `healthcheck.htm`, одинаковым входом и набором серверов сгруппированы визуально. Каждая служба сохраняет собственный backend и настройки; это не автоматическое преобразование в модель Exchange.

Полный импорт по-прежнему консервативен. Разбор экранированных пробелов, кавычек и inline-комментариев больше не блокируется посторонним `listen stats`. Комментарии переносимых строк сохраняются. Неподдерживаемые конструкции остаются ручными.

Ограничения полного импорта: произвольные составные ACL, общие пулы, TCP payload/WAIT_END, нестандартные tcp-check, несколько/named defaults, точные дробные тайм-ауты и сложные смешанные политики не преобразуются в редактируемую модель автоматически. Они видны в обнаружении; частичное изменение адресов сохраняет такие параметры, в том числе `500ms`, без округления. Динамические backend и нестандартные адреса серверов требуют просмотра исходного конфига. Полный импорт дополнительных `.cfg` не выполняется.

## Проверки

- Регрессионные тесты включают обезличенные топологии прямой TLS-терминации и смешанной SNI/TLS-схемы. Они используются для обнаружения и разбора, не являются готовыми конфигами установки.
- Проверяется реальный HTTPS-редирект RD Web через запущенный HAProxy, независимость других доменов и POST-запросов.
- Проверяются откат reload, локальная проверка Studio, смена public_url, ротация сертификатов, полные/неполные цепочки и сохранение комментариев.
- Матрица синтаксиса: 36 синтетических конфигураций на ветках HAProxy 2.4, 2.6, 2.8, 3.0, 3.2, 3.3, 3.4. Это не проверка всех функций Windows Exchange/RDS.
- Определение AWS-LC и исправление DH покрыты регрессионными тестами; отдельная реальная сборка HAProxy с AWS-LC в локальном прогоне не запускалась.

Локальный прогон 25.11.2026: **158 тестов прошли**, **252 проверки синтаксиса** (36 конфигураций × 7 веток) прошли. Chromium: сценарии частичного редактирования, RD Web и публикации Studio проверены на 1440/390/320 px; axe и проверка горизонтального переполнения ошибок не обнаружили. Рабочие серверы этим прогоном не изменялись.
