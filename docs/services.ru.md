# Публикация сервисов без синтаксиса HAProxy

В разделе «Сервисы» нажмите «Добавить сервис». Мастер состоит из трёх шагов:

1. Название и тип сервиса. Шаблон подставляет обычные порты и режим передачи.
2. Внешний адрес, внутренние серверы и шифрование. Для сайта укажите домен и при необходимости путь. Укажите IP внутреннего сервера и порт уже работающего приложения. Для HTTPS выберите сертификат или загрузите новый.
3. Проверьте схему, проверьте TCP-доступность серверов и при необходимости задайте дополнительные настройки. Нажмите «Проверить и опубликовать», прочитайте результат проверки и подтвердите применение.

Панель проверит конфликт портов и маршрутов, запустит проверку установленного HAProxy, сохранит резервную копию и выполнит настроенную перезагрузку. Если runtime API был доступен, публикация дополнительно проверяет появление нового процесса HAProxy. При неудаче восстанавливается предыдущий файл. История и редактор сохраняют совместимость с публикациями из мастера.

## Шаблоны

| Сервис | Внешний порт по умолчанию | Режим |
|---|---:|---|
| Сайт HTTPS, WebSocket | 443 | Сертификат на HAProxy, HTTP или TLS до сервера |
| Сайт HTTP | 80 | HTTP |
| RDP | 3389 | Прозрачный TCP, нативная защита на сервере Windows |
| RDS: прямой RDP через брокер | 3389 | RDP-вход брокера/redirector либо токенная маршрутизация msts; [инструкция](rds.ru.md) |
| RD Gateway / RD Web Access | 443 | Сквозной TLS до Windows, общий SNI или отдельный IP; [инструкция](rd-gateway.ru.md) |
| SSH | 22 | Прозрачный SSH; если 22 занят SSH хоста, выберите другой внешний порт |
| SMTP | 25 | Прозрачный SMTP/STARTTLS |
| Отправка SMTP submission | 587 | Прозрачный SMTP/STARTTLS |
| SMTPS | 465 | Сквозной TLS либо сертификат на HAProxy |
| IMAP | 143 | Прозрачный IMAP/STARTTLS |
| IMAPS | 993 | Сквозной TLS либо сертификат на HAProxy |
| POP3 | 110 | Прозрачный POP3/STARTTLS |
| POP3S | 995 | Сквозной TLS либо сертификат на HAProxy |
| ManageSieve | 4190 | Прозрачный протокол/STARTTLS |
| MySQL | 3306 | Нативный TCP |
| PostgreSQL | 5432 | Нативный TCP с сохранением согласования TLS |
| Redis | 6379 | TCP |
| Другой TCP | 8080 | Прозрачный TCP |
| Другой TLS | 8443 | Сквозной TLS либо сертификат на HAProxy |

Любой внешний и внутренний порт можно изменить. Для RDP, SSH, SMTP, IMAP, POP3 и PostgreSQL нельзя подменять нативное согласование безопасности обычной TLS-терминацией: мастер ограничивает несовместимые режимы. Для SMTPS/IMAPS/POP3S при выборе TLS-терминации обычный внутренний порт автоматически меняется на 25/143/110, если пользователь ещё не заменил его. Политика relay, пароли почты и учётные записи остаются на почтовом сервере.

## Сертификаты

Поддерживаются PEM/CRT с цепочкой и отдельным KEY, объединённый PEM, а также PFX/P12 с паролем. Лимит каждого файла — 512 КБ. Мастер проверяет дату действия, соответствие ключа и сертификата, а при публикации сайта — покрытие домена. Новый PEM получает случайное имя и права 0600; существующие сертификаты не перезаписываются. Ключ и пароль импорта не возвращаются в API и не попадают в журнал. Используется установленный OpenSSL. Автоматическая выдача и продление ACME в эту версию не входят.

## Дополнительные настройки

Можно выбрать несколько внутренних серверов, веса и резервные узлы; балансировку по очереди, по числу соединений или по IP; TCP- и HTTP-проверки с отдельной страницей; таймаут, интервал проверок и лимит соединений; разрешённые IP/CIDR клиентов; TLS до внутреннего сервера с проверкой сертификата и SNI; подмену Host, удаление префикса пути, HSTS и PROXY protocol v2. Проверка TLS включена по умолчанию при включении TLS к серверу; CA определяется для Debian/Ubuntu и RHEL-подобных систем, либо задаётся через ca_bundle.

PROXY protocol включайте только если внутренний сервер его поддерживает. Для RDP, SSH и баз данных доступно ограничение источников по IP. Проверка TCP подтверждает соединение с портом, а не готовность приложения или правильность пароля.

## Существующие публикации и изменения

Мастер может добавлять новые веб-домены к совместимому HTTP/TLS-входу, не занимая второй раз тот же порт. Префикс пути может расширять существующий домен; его приоритет показывается перед применением. Полная замена домена, уже занятого ручными правилами, блокируется. Несовместимый TCP/TLS-вход, занятый системный порт и пересекающиеся управляемые маршруты отклоняются.

Сервисы из мастера можно изменять, выключать, включать и удалять. Удаление убирает только их публикацию; внутренний сервер и сертификат остаются. В конфиге хранятся проверяемые служебные блоки и описание выбранных полей. Их ручное изменение блокирует последующее использование мастера до восстановления целостности. Дополнительные .cfg участвуют в обнаружении конфликтов и проверке, но мастер редактирует только основной файл.

## Что остаётся вне панели

DNS должен указывать на публичный адрес HAProxy, внутреннее приложение должно быть запущено, внешний TCP-порт должен быть разрешён в firewall/маршрутизаторе и у провайдера. Мастер не меняет DNS у регистратора, облачные сетевые правила и не устанавливает внутренние приложения. Общий UDP, QUIC/HTTP3 и произвольные директивы HAProxy этим мастером не генерируются; сложные ручные сценарии остаются в редакторе. Docker-вариант по-прежнему работает только в режиме наблюдения; публикация и загрузка ключей требуют нативной установки с нужными правами.

Расширенные группы доменов, Exchange и SNI описаны в [отдельной инструкции](exchange-sni.ru.md).

## Существующие публикации и общий HTTPS-вход

Версия 0.7 сохраняет в модели сервиса дополнительные настройки существующих публикаций: HTTP-коды и адреса перенаправлений, cookie-привязку серверов, таймаут туннеля, версию HTTP и Host для проверок, проверку сертификата сервера и PROXY protocol в проверках, фиксированную версию TLS до сервера, правила путей и ответ вне маршрутов. Эти параметры доступны в дополнительных настройках мастера. Проверяйте разницу перед применением.

Если внешний TCP/443 передаёт TLS на локальный HTTP frontend (например, `127.0.0.1:8443`), в мастере HTTPS выберите существующий HTTPS-вход. Внешний порт остаётся 443. Панель проверяет цепочку `default_backend` → локальный сервер → TLS bind и согласованность PROXY protocol. Локальный порт 8443 наружу открывать не требуется. Транспортный backend-мост остаётся частью инфраструктуры.

Для HTTP можно выбрать действие «Перенаправление» без внутренних серверов. Префикс пути можно сопоставлять с границей сегмента либо как исходный префикс; это позволяет сохранить существующие правила Exchange.

Начиная с 0.8 простые существующие публикации можно переносить через **Сервисы → Импортировать конфиг**; [пошаговая инструкция и ограничения](import.ru.md). Для сложных правил остаётся ручное сопоставление с моделями сервиса и проверка сохранения маршрутизации, заголовков, TLS, проверок доступности и ограничений путей. После переноса они отображаются в «Сервисах» и редактируются мастером. Служебные frontend, stats и локальные транспортные мосты остаются в базовом конфиге. Тип перенесённого сервиса закреплён, чтобы смена шаблона случайно не сбросила его настройки.

## Названия серверов и статусы мониторинга

Начиная с 0.7.1, в обзоре для управляемых публикаций отображаются название сервиса, адрес внутреннего сервера и путь маршрута, если он есть. Технические имена в конфиге (например, `node1` и `studio_be_…`) сохраняются: для понятных подписей переименовывать их и перезагружать HAProxy не требуется. Для ручных backend используются исходные имена.

Общий статус сервиса учитывает основной пул, если он используется, и отдельные пулы маршрутов. Для Exchange это, например, проверки OWA, MAPI, EWS и Autodiscover. Запрещённые пути не считаются неисправными службами.

| Статус | Значение |
| --- | --- |
| Сервер доступен | В каждом используемом пуле есть сервер со статусом UP |
| Частично доступен | Часть пулов доступна, у остальных серверы недоступны или ещё нет данных |
| Сервер недоступен | Доступных пулов нет; полученные проверки не подтверждают доступность |
| Ожидание данных | Нет данных runtime для нужного пула и ни один пул ещё не подтверждён как доступный |
| Проверки выключены | Проверки доступности отключены; это не подтверждение работоспособности приложения |
| Перенаправление настроено | HTTP-сервис только перенаправляет запросы; backend и его проверки не нужны |
| Выключен | Публикация отключена в панели |

«Перенаправление настроено» подтверждает настройку правила, а не доступность целевого URL. Статусы серверов отражают проверки HAProxy и не заменяют проверку входа пользователя в приложение.

Чтобы получить исправления 0.7.1, в каталоге клонированного репозитория на сервере выполните:

```bash
git pull --ff-only
sudo sh scripts/install.sh
sudo systemctl restart haproxy-studio
```

После обновления обновите страницу браузера через Ctrl+F5. Эти команды обновляют и перезапускают панель; рабочий конфиг HAProxy, пользователи и сертификаты сохраняются. Сама установка панели не перезагружает HAProxy.

## Читаемые маршруты и серверы

Начиная с 0.8.1 раздел **Маршруты и серверы** показывает публикации по названию сервиса, домену, пути и адресу назначения. Например: «Почта компании · mail.example.org · /owa → 192.0.2.10:443». Понятные подписи берутся из сохранённых моделей сервисов и доступны даже при недоступном runtime socket.

Входы подписываются по роли: HTTP, HTTPS, общий TLS-вход с SNI, локальный вход HTTPS или статистика HAProxy. Локальный транспортный backend к HTTPS-входу определяется по адресу назначения и подписывается как «Локальная обработка HTTPS». Сам по себе он не является отдельным опубликованным приложением.

Отдельно видны HTTP→HTTPS, перенаправление корня сайта, добавление завершающего `/`, запрещённые пути и ответы вне маршрутов. Для TCP показывается условие подключения, для SNI — выбор по домену и маршрут по умолчанию. HTTP-исключения отображаются со своими путями. В разделе «Сервисы» у TLS-публикации с SNI отображается её домен и порт.

Точные имена frontend/backend/server и условия ACL находятся в **Технических деталях**; кнопка **Конфигурация** открывает соответствующее место файла. Неизвестные ручные условия не переводятся предположительно: у них сохраняется отметка ручного правила и доступ к исходному условию. Ручные группы серверов доступны для удаления отдельно; управляемые группы изменяются через «Сервисы».

Поиск работает по названию сервиса, домену, адресу, порту и техническим идентификаторам. Новое представление меняет только интерфейс: существующие имена и правила в `haproxy.cfg` не переименовываются, перезагрузка HAProxy для отображения не нужна. После обновления панели перезапустите `haproxy-studio` и обновите браузер через Ctrl+F5.

## Имена backend и серверов в конфигурации

В 0.9 можно задавать настоящие имена backend и серверов на шаге «Адреса и защита». Новые публикации используют понятные имена по умолчанию. Существующие имена меняются через отдельную проверяемую операцию «Понятные имена в конфиге» либо через поля конкретного сервиса. [Примеры, ограничения и порядок переименования](names.ru.md).
