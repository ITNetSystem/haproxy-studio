# Импорт существующего конфига

В HAProxy Studio 0.8 появился мастер **Сервисы → Импортировать конфиг**. Он переносит распознанные публикации в управляемые сервисы, которые затем можно изменять, выключать и удалять через обычный мастер.

Импорт доступен администратору в нативной установке с включённым управлением. В режиме наблюдения, в том числе в стандартном Docker-варианте, применение недоступно.

## Порядок действий

1. Откройте **Сервисы → Импортировать конфиг**.
2. Выберите источник: **текущий конфиг этого HAProxy** или **загрузить haproxy.cfg**. Загружаемый файл — текст UTF-8 размером до 512 КиБ. Анализируется основной файл; дополнительные `.cfg` не импортируются и остаются на сервере.
3. Нажмите **Проанализировать конфиг**. Рабочий файл на этом этапе не меняется.
4. В списке найденных публикаций проверьте домены, внешний порт, внутренние серверы и предлагаемый тип. Снимите отметки с ненужных публикаций и задайте понятные названия.
5. Прочитайте список **Останутся ручными**. В нём указаны причины, по которым отдельные правила пока нельзя перенести автоматически.
6. Если источник — загруженный файл, подтвердите **замену основного конфига этим файлом**. Это не объединение двух конфигов: старые правила, которых нет в загруженном файле, исчезнут из активного конфига после применения.
7. Нажмите **Проверить перенос**. Панель проверит итог установленным HAProxy и покажет разницу относительно текущего рабочего конфига.
8. Проверьте всю разницу и предупреждения. Только кнопка **Применить изменения** записывает конфиг, предварительно сохранив резервную копию, и выполняет плавную перезагрузку HAProxy. При ошибке применения панель восстанавливает предыдущий конфиг.
9. Откройте **Сервисы**, проверьте статусы и проверьте реальные подключения пользователей. Предыдущие версии доступны в **Истории изменений**.

Закрытие проверки без применения ничего не записывает. Если основной или дополнительный конфиг изменился после анализа, повторите анализ: устаревший план не применяется.

## Что распознаётся автоматически

| Схема | Поддержка |
| --- | --- |
| HTTP/HTTPS по домену | Один простой ACL `hdr(host)` либо `hdr(host),lower,field(1,:)`, условие `use_backend … if ACL`, отдельный backend. Для HTTPS поддерживается нормализованный Host без порта |
| Несколько доменов одной публикации | Имена в одном ACL становятся основным доменом и дополнительными доменами |
| TLS по SNI | Один ACL `req.ssl_sni` или `ssl_fc_sni` и отдельный backend; режим должен соответствовать TLS на bind |
| TCP без домена | `frontend` с `default_backend`, например проброс RDP или почтового порта. Сохраняются исходный frontend и его настройки; в сервис переносится пул |
| HTTP-перенаправления | Отдельный HTTP-вход с простыми редиректами по одному ACL домена, явным кодом и схемой HTTPS либо полным URL |
| Пулы серверов | Явные IP/имена и порты, веса и резервные серверы; roundrobin, leastconn, source; одинаковые поддерживаемые TLS и health-параметры серверов |
| Простые проверки | TCP, SMTP EHLO и `option httpchk` с методом/путём/версией HTTP и ожидаемым статусом |

Импорт консервативный: вся политика распознаваемого пула должна быть понятна мастеру. Например, автоматически переносится `timeout connect 5s`, а иные значения оставляются для ручной настройки. Неодинаковые параметры проверок серверов, дополнительные директивы и неоднозначное наследование не угадываются.

Для HTTPS сертификаты bind должны уже находиться в настроенном каталоге сертификатов панели и покрывать домены публикации. При переносе на другой сервер заранее разместите сертификаты с ключами, CA, errorfile, map-файлы и остальные зависимости по корректным путям. Сам `haproxy.cfg` этих файлов не содержит. Итоговая проверка использует пути и версию HAProxy **на целевом сервере**.

## Что сохраняется ручным

В первой версии автоматически не преобразуются произвольные условия ACL и логические выражения, Exchange с маршрутами по путям, общие backend для нескольких публикаций, динамический выбор backend через map, правила stick-table, нестандартные проверки, секции `listen`, HTTP-входы только с `default_backend` без доменных правил и цепочки через локальный TLS-мост/`accept-proxy`.

Нераспознанные и невыбранные правила сохраняются **в выбранном источнике**. Для текущего конфига это действующие правила сервера; для загрузки — правила из загруженного файла. Сам факт сохранения этих строк не гарантирует полной эквивалентности всей новой конфигурации: перед применением нужно проверить взаимодействие правил.

Уже управляемые сервисы из выбранного источника сохраняются и повторно не предлагаются. Сложные публикации можно перенести вручную с использованием расширенных параметров мастера и проверкой поведения; [параметры существующих публикаций](services.ru.md#существующие-публикации-и-общий-https-вход).

## Что означает успешная проверка

Успешный `haproxy -c` подтверждает синтаксис и доступность зависимостей, проверяемых самим HAProxy. Он не доказывает доступность DNS, правильность внешнего firewall, работоспособность приложения, Windows-аутентификации или полную эквивалентность старых и новых правил. После переноса проверьте реальные HTTP/TLS, почтовые или RDP-подключения для выбранных публикаций.

Технические имена backend и серверов после переноса могут измениться на `studio_be_…` и `node1`. Это видно в разнице конфигов; панели мониторинга и внешние скрипты, использующие старые имена, потребуется учесть. В Studio серверы подписаны названием сервиса и адресом.

## Обновление до 0.8

В каталоге клонированного репозитория на сервере:

```bash
git pull --ff-only
sudo sh scripts/install.sh
sudo systemctl restart haproxy-studio
```

Обновите страницу браузера через Ctrl+F5. Установка обновления сама по себе не импортирует конфиг и не перезагружает HAProxy: перенос запускается отдельно через мастер.
