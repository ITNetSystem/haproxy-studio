# RDS через HTTPS: RD Gateway и RD Web Access

Внешний доступ через HTTPS и прямой RDP через брокер — разные схемы. В HAProxy Studio 0.6 доступны отдельные шаблоны:

| Шаблон | Внешний порт | Внутренний порт | Для чего |
|---|---:|---:|---|
| **RDS: RD Gateway — шлюз HTTPS** | 443/TCP | 443/TCP | Подключение клиента удалённого рабочего стола через HTTPS-шлюз Windows |
| **RDS: RD Web Access — портал HTTPS** | 443/TCP | 443/TCP | Портал IIS с приложениями и рабочими столами, обычно `/RDWeb/` |
| **RDS: прямой RDP через брокер (3389)** | 3389/TCP | 3389/TCP | Прямой RDP-вход или маршрутизация на Session Host по токену брокера; [отдельная инструкция](rds.ru.md) |

Панель не устанавливает роли Windows, не создаёт коллекции, лицензии, CAP/RAP, NPS/MFA и сертификаты. Они должны быть настроены в вашем RDS-развёртывании до публикации.

## Почему используется сквозной TLS

Оба HTTPS-шаблона передают исходный TLS до Windows, не разбирая HTTP/RPC и не меняя авторизацию. Сертификат устанавливается **на Windows RD Gateway/IIS**, покрывает публичный домен и должен быть доверенным для клиентов. Загружать его приватный ключ на HAProxy для этих шаблонов не нужно.

До Windows не добавляется PROXY protocol и не создаётся второй слой TLS. TCP-проверка подтверждает только доступность порта, не успешную авторизацию RDS. Она не проверяет срок сертификата или готовность коллекции.

## Пошагово: RD Gateway

1. Убедитесь, что роль RD Gateway настроена, слушает HTTPS/443, принимает ваш домен и может обращаться к внутренним RDS-серверам. Проверьте политики доступа и сертификат.
2. Создайте DNS-запись домена, например `rdg.example.org`, на внешний адрес HAProxy/NAT или внутренний адрес для локальных клиентов.
3. В панели откройте **Сервисы → Добавить сервис**. Задайте имя и выберите **RDS: RD Gateway — шлюз HTTPS**.
4. На шаге «Адреса и защита» оставьте внешний порт **443**. В поле доменов SNI укажите `rdg.example.org`. Внутренний сервер — адрес Windows RD Gateway, порт **443**. Это не RDP-порт Session Host 3389 и не локальный порт TLS-терминатора HAProxy 8443.
5. Если используете общий TCP/SNI-вход 443, оставьте разделение по SNI включённым и fallback выключенным. У существующего входа должны быть TCP mode, TLS без расшифровки и `tcp-request inspect-delay`; его другие SNI-правила и backend по умолчанию сохраняются.
6. Если нужен отдельный выделенный IP/порт, задайте его и при необходимости выключите разделение по SNI. Тогда все соединения к этому входу направляются в выбранный пул, в том числе от клиентов без SNI. Этот IP/порт должен быть свободен.
7. Для нескольких Windows Gateway добавьте все узлы. По умолчанию используется **балансировка по IP клиента**, чтобы связанные TCP/RPC-каналы попадали на один узел. Пользователи за одним NAT могут попадать на один шлюз. Выбирайте другой алгоритм только с учётом устройства вашей фермы.
8. Таймаут Gateway по умолчанию — **8 часов**; в дополнительных настройках его можно изменить. В backend также задаётся `timeout tunnel` для долгих соединений. Если требуется, ограничьте разрешённые IP клиентов.
9. Проверьте внутренние серверы, нажмите проверку публикации, прочитайте предупреждения и примените конфигурацию.
10. В клиенте Remote Desktop укажите `rdg.example.org` как **сервер RD Gateway**. Адрес ресурса/коллекция задаются отдельно средствами RDS или в выданном RDP-файле. Портал в браузере не заменяет настройку шлюза в клиенте.
11. Проверьте реальный вход, переподключение и продолжительный сеанс. Тесты HAProxy Studio не запускают полноценный Windows RDS.

## UDP/3391

Шаблон передаёт только **TCP/443**. UDP/3391, который RD Gateway может использовать для RDP over UDP, через этот TCP frontend не публикуется. Если UDP-транспорт нужен, настройте отдельный NAT/UDP-балансировщик и соответствующую доступность серверов. Не заменяйте это открытием UDP/3389 или включением TLS на UDP-порту. Проверяйте, разрешён ли в вашем развёртывании TCP-транспорт для используемых клиентов.

## Пошагово: RD Web Access

1. Проверьте, что IIS с ролью RD Web Access обслуживает `https://имя-сервера/RDWeb/` и имеет подходящий сертификат.
2. Если Gateway и Web работают **на одном сервере под одним публичным доменом**, создайте **одну публикацию RD Gateway**. Она передаёт TLS целиком, поэтому запросы `/RDWeb/` тоже попадут в IIS. Вторая публикация на тот же домен/порт не нужна и будет отклонена как конфликт.
3. Если портал имеет отдельный домен или сервер, выберите **RDS: RD Web Access — портал HTTPS**, задайте домен SNI, внешний 443 и адрес IIS:443.
4. Проверьте и примените публикацию. Откройте **`https://rdweb.example.org/RDWeb/`**. Перенаправление `/` в `/RDWeb/` настраивается в IIS: HAProxy в этой схеме не расшифровывает HTTP и не переписывает пути.
5. Для удалённых рабочих столов извне дополнительно должен быть настроен RD Gateway, указанный в настройках RDS/выдаваемых RDP-файлах. Сам по себе портал не делает Session Host доступными через HTTPS.

## Если 443 уже занят

- **TCP/SNI без расшифровки:** шаблоны могут добавить новый SNI-домен в существующий вход основного конфига, сохранив его bind и default backend. Клиент должен отправлять SNI. Поддержку проверьте на ваших версиях клиентов.
- **Клиент не отправляет SNI:** для него нужен отдельный IP/порт или осознанно выбранный fallback. На общем входе допускается только один fallback; мастер не заменяет существующий.
- **HTTPS frontend в режиме HTTP с `bind ... ssl crt ...`:** готовые новые шаблоны не переводят этот вход в passthrough. Нужен отдельный IP/порт или согласованная переделка внешнего входа под TCP/SNI. Это не исправляется заменой внутреннего порта на 8443.
- **Домен уже обслуживается ручным HTTP frontend за SNI fallback:** прямой новый SNI-маршрут перехватит его раньше. Панель блокирует такой перенос; сначала спланируйте миграцию существующего маршрута или используйте другое имя.
- **Вход находится в `conf.d`:** мастер не вставляет в него управляемые блоки. Для этой схемы нужен свободный IP/порт либо ручная настройка существующего входа.

Не удаляйте и не меняйте общий frontend только ради новой публикации: он может обслуживать другие приложения. [Разбор двухступенчатой HTTPS-схемы](installation.ru.md#постоянный-доступ-по-https).
