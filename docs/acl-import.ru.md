# Импорт ACL и общих backend — 0.13

Несколько почтовых доменов могут использовать один backend. Для импорта не нужно создавать копию пула под каждый домен или упрощать проверки Exchange.

Например, эти правила можно перенести вместе:

```haproxy
acl organization_a hdr(host),lower,field(1,:) -i mail.a.example.org autodiscover.a.example.org
acl organization_b hdr(host),lower,field(1,:) -i mail.b.example.org autodiscover.b.example.org
acl owa path_beg -i /owa

use_backend exchange_pool if organization_a owa
use_backend exchange_pool if organization_b owa
```

В Studio появится одна ACL-публикация с четырьмя доменами, ссылающаяся на существующий `exchange_pool`. Сам backend останется в исходном конфиге **в одном экземпляре**.

## Как перенести

1. Обновите приложение и откройте **«Сервисы» → «Импортировать конфиг»**.
2. Выберите текущую конфигурацию или загрузите файл и нажмите **«Проанализировать конфиг»**.
3. Выберите найденные ACL-публикации. Дайте им понятные имена: например, «Exchange — компании A и B».
4. Проверьте предлагаемые изменения и результат `haproxy -c -V`, затем примените.
5. В списке сервисов доступны **«Изменить»** для имени и доменов и **«Общий пул»** для адресов серверов.

Для разных frontend, использующих один backend, создаются отдельные публикации с общей ссылкой на тот же пул. Можно переносить их последовательно; пул не удаляется и не копируется. Ссылки из оставшихся ручных правил продолжают работать.

## Какие ACL поддерживаются

- Точные доменные ACL по `hdr(host)`, `hdr(host),lower,field(1,:)`, `req.ssl_sni`, `req_ssl_sni` и `ssl_fc_sni`.
- Несколько доменов в одном ACL и повторные объявления одного доменного ACL.
- Именованные условия с неявным AND, `or` и `||`.
- Отрицания при наличии положительного ограничения доменов, например `organization_a !excluded owa`.
- Дополнительные именованные ACL путей, IP и других условий: их определения сохраняются в frontend, а ссылки остаются в исходных сочетаниях.
- Анонимные условия точного Host/SNI, например `{ ssl_fc_sni -i mail.example.org }` или `{ ssl_fc_sni mail.example.org }`. Чувствительность к регистру сохраняется. Поддерживается явное `-m str`.
- Одновременные HTTP-редиректы, заголовки и backend-маршруты: исходные HTTP-политики не заменяются.
- Прямая TLS-терминация и проверяемая схема TCP/SNI → локальный HTTPS с PROXY protocol. Поддерживаются как default-мост, так и условный `use_backend` на внешний SNI.

Это не преобразование ACL в один общий HTTP-backend. Каждое исходное правило выбора backend сохраняет своё место относительно других маршрутов. При объединении условий OR отдельные ветви направляются в тот же backend в той же позиции.

## Изменение доменов

В «Изменить» укажите основной домен и дополнительные домены либо список SNI.

Если дополнительные условия одинаковые, новый домен получает тот же профиль маршрутизации. Если правила отличаются, выберите **«Как обрабатывать добавленные домены» → «Как существующий-домен»**. Studio воспроизведёт сочетания дополнительных ACL и позиции маршрутов выбранного домена; угадывать нужные правила она не будет. Выбранный образец применяется ко всем доменам, добавленным к этой импортированной публикации сверх исходного списка.

В смешанной схеме домен должен уже направляться внешним SNI-входом к нужному внутреннему HTTPS-входу. При необходимости сначала добавьте его во внешнюю SNI-публикацию, затем во внутреннюю HTTP-публикацию. Связь проверяется перед применением. При TLS-терминации сертификаты существующего bind должны покрывать новые имена.

Отдельные ACL frontend, используемые редиректами и другими ручными правилами, сохраняются. Изменение доменов импортированной публикации изменяет её backend-маршруты, а не все упоминания домена во всём конфиге.

## Общий пул

Кнопка **«Общий пул»** открывает редактор адресов и портов. Предварительный просмотр показывает затронутые входы. Изменение затронет все использующие backend публикации, включая ручные.

Остальные параметры backend сохраняются буквально: TLS/SNI/CA, SMTP и TCP-проверки, HTTP health checks, cookies, persistence, веса, backup/disabled, slowstart, точные тайм-ауты вроде `500ms`, комментарии и неизвестные директивы. Они не подменяются значениями по умолчанию мастера. Для изменения этих параметров используйте редактор конфигурации.

Отключение или удаление ACL-публикации убирает только принадлежащие ей маршруты. Общий backend остаётся на месте. Другие правила и `default_backend` могут продолжить обработку запросов: отключение маршрута не является запретом доступа по домену. Пул, на который ссылается даже выключенная импортированная публикация, защищён от удаления.

## Ограничения

Остаются ручными условия без конечного положительного списка доменов, например `unless organization_a` или только `!organization_a`; regex/suffix-домены без такого ограничения; неподдерживаемые вложенные и анонимные недоменные выражения; динамический выбор backend и `server-template`. Разные способы сопоставления Host в одной публикации и смешанные правила регистра в одной ветви требуют ручной проверки.

SMTP 25/587 с STARTTLS не предоставляет SNI с первого байта. ACL по содержимому SMTP и выбор почтового сервера по получателю автоматически в доменные TLS-маршруты не превращаются.

Импорт дополнительных `.cfg` и нескольких/named defaults по-прежнему ограничен существующим импортёром. Сертификаты и внешние файлы нужно заранее разместить на сервере. Перед применением проверяются исходная и предлагаемая конфигурации; невалидный предлагаемый конфиг не применяется.

Служебные комментарии `# studio-acl-slot` задают положение перенесённых правил: не удаляйте и не перемещайте их вручную. Повреждение мест вставки или удаление используемых ACL блокирует генерацию; восстановите нужную версию из истории.

## Проверки

Регрессионные тесты проверяют общий пул без копирования, AND/OR и отрицания, чувствительность к регистру, выбор образца домена, разные frontend, повторный импорт, no-op, отключение и удаление публикаций, адреса общего пула, сохранение неизвестных параметров и защиту от удаления зависимостей.

На запущенном HAProxy сравниваются ответы до и после импорта: обычная HTTP-маршрутизация с чередующимися правилами и TLS через условный SNI-мост с PROXY protocol. Для анализа используются также обезличенные копии двух инфраструктурных конфигураций. Это не проверка всех функций живого Exchange или Windows RDS.

Локальная проверка релиза 0.13: **172 теста прошли**, **273 проверки синтаксиса** (39 конфигураций × 7 веток HAProxy) прошли. В Chromium проверены импорт, изменение доменов, выбор образца, состояние общего пула и предварительный просмотр изменения серверов на ширинах 1440/390/320 px; ошибок axe, горизонтального переполнения и JavaScript не обнаружено.

## Сертификаты общего frontend — 0.13.1

Список `crt` на входе 443 может содержать сертификаты многих доменов. Сертификат первого домена в списке не является сертификатом каждого backend этого frontend.

При анализе ACL-публикаций Studio сохраняет исходный TLS-вход и показывает истёкшие, ещё не действующие и нечитаемые сертификаты отдельно: один раз на сочетание frontend/PEM, в разделе «Предупреждения об исходной конфигурации». Срок чужого сертификата не исключает все маршруты из результатов анализа. Импорт не удаляет и не заменяет проблемный PEM автоматически.

Если файл отсутствует или HAProxy отвергает конфигурацию, просмотр результатов анализа остаётся доступным, но применение не разрешается до исправления. При добавлении нового домена по-прежнему проверяется покрывающий его действующий сертификат. Для новых управляемых публикаций истёкший сертификат, покрывающий именно их домен, остаётся ошибкой.

Служебный одиночный TCP → локальный HTTPS-мост больше не предлагается для обычного переноса как отдельное TCP-приложение: он нужен другим публикациям и сохраняется в исходной конфигурации.

Дополнительно исправлен импорт `ssl_fc_sni` внутри HTTPS frontend: такой маршрут сохраняет выбор по SNI и продолжает использовать HTTP-backend.

Проверка исправлений: 182 теста прошли; 41 конфигурация проверена на семи ветках HAProxy — 287 успешных проверок синтаксиса. В Chromium проверены импорт с реальным просроченным сертификатом на общем frontend и явная замена существующего RDS-портала, включая 1440/390/320 px и axe.

## Дополнения 0.16

Сохранение исходного пула применяется и к одиночной доменной публикации, если её параметры нельзя точно выразить типовым backend. TLS-вход сохраняет исходные зависимости `crt-list`, `crt-base`, внешние файлы и каталоги сертификатов. Эти файлы не копируются при импорте: на целевом сервере они должны существовать, а полный конфиг должен пройти `haproxy -c`. [Результаты проверки и ограничения](project-check-0.16.ru.md).

## Готовый файл Studio: 0.16.1

Если загруженный файл уже содержит служебные записи сервисов, количество новых публикаций может быть 0. Это не означает, что сервисы потеряны. Анализ покажет «Готовая конфигурация Studio: сервисов N». Подтвердите замену основного конфига и нажмите «Проверить загрузку готовой конфигурации», затем проверьте diff и подтвердите применение. При отсутствии выбранных новых публикаций файл не перегенерируется. Предупреждения о сертификатах относятся к исходному TLS-входу и не объясняют отсутствие новых кандидатов. Сертификаты, ключи и дополнительные файлы по-прежнему нужно разместить на целевом сервере отдельно.

## Сохранение доступа к Studio: 0.16.2

Готовый конфиг с другого сервера не обязательно содержит публикацию самой панели. Если текущая конфигурация содержит статический маршрут к локальной Studio, а новая его удаляет, проверка и применение блокируются до записи файла и перезагрузки. Учитываются дополнительные `.cfg` и прямой `listen`. Сначала перенесите маршрут панели в новый конфиг с правильными доменом, сертификатом, `base_path` и локальным портом. Эта защита не доказывает корректность всех ACL/TLS-условий и не заменяет проверку публичного доступа.

## Единый Exchange: 0.17

Связанные импортированные службы Exchange автоматически показываются общей карточкой с одним редактором и применением. Backend, исходные ограничения и отдельные проверки сохраняются. [Группировка, параметры и ограничения](exchange-unified.ru.md).
